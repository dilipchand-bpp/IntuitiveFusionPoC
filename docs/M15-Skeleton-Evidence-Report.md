## 2. The stitched journey (what "skeleton works end to end" means)
One test, in the order the business runs it, each stage done by the person who does it, each hand-over checked:

1. Requester describes the need to the assistant, answers its questions, reviews and submits.
2. Procurement submits the drafted plan; the delegate approves and locks it.
3. Procurement builds the tender pack; the delegate gives permission to publish; procurement publishes.
4. Two suppliers register from invitations and submit sealed bids; the tender closes (closing time moved by the test-only entry point).
5. Procurement opens the evaluation with a panel; every member declares no conflict, then everyone scores; the chair opens consensus, saves and locks it (ranking shown).
6. Procurement generates the report; the delegate approves it.
7. Legal drafts the contract from the approved report and releases it; the delegate signs; it locks.
8. The contract manager sees the signed contract's record and its scheduled alerts.
9. The executive sees the procurement on the dashboard with its plan, tender and evaluation ticks.
10. Probity finds every stage (request, plan, tender, evaluation, report, contract) in the audit trail.

Done through the API rather than the screen, because they are long repetitive forms already covered screen by screen in the module tests: the suppliers' uploads and the evaluators' conflict declarations and scores.

How "Pass" is decided, and what it is not: a working requirement passes when **every user story it traces to is named in an automated test that passed in this run**. The enabler stories that tests cover without naming (audit, RBAC, accessibility, notifications, AI governance) are mapped to the specific test files in the generator. This is traceability by reference. It does not prove every acceptance criterion of a requirement is asserted.

Working requirements that are **not** fully verified:
- Not traced (4): NFR-P03 and NFR-P06 (downstream fields update dynamically; no test), NFR-AV05 (availability) and NFR-CA02 (capacity): no test or measurement exists for these in the proof of concept.
- Evidence only (5): NFR-M02, SEC-AP03, SEC-AP06, SEC-AP07 (secure delivery: verified by the pipeline definition and its green runs, including the secret scan, not a test file) and PRM-09 (no secrets, input validation: partly by the pipeline and tests, no single test asserts it).

## 6. What could not be done
- **Lighthouse**: attempted with Edge (headless and visible) against the production build; Lighthouse reported "page did not paint any content" (NO_FCP) every time in this environment, so no scores were produced and none are claimed. The axe results above use the same accessibility engine and cover far more pages. A Lighthouse run needs a different browser setup (for example Chrome on a CI runner); this is recorded for M17.
- No performance numbers: the k6 script from M0 has still never been run (M17).
